# Prompt de trabajo — v0.3

Alcance de DESIGN.md §9 para v0.3: gateway propio en Go, multi-nodo y cloud burst controlado.

## Decisiones (DESIGN.md §11)

- **`gd-gateway` sustituye a LiteLLM y a Postgres.** Es un proxy inverso en Go (solo stdlib)
  compatible con la API de OpenAI que añade lo que Guardian necesita: llaves virtuales, lista de
  modelos por llave, límite de peticiones por minuto, presupuesto, auditoría y enrutado a varios
  nodos. Ollama ya expone `/v1/*` compatible con OpenAI, así que el gateway no traduce formatos:
  autentica, filtra, enruta, mide y reenvía (incluido el streaming SSE).
- **Almacén sin base de datos**: las llaves (hash SHA-256, nunca el valor) y los contadores de
  uso viven en archivos JSON en un volumen (`gateway_data`), con escritura atómica. Un homelab
  no necesita Postgres para esto y se elimina el contenedor más pesado de la plataforma.
- **Multi-nodo = varios upstreams por modelo.** `compose/gateway/config.yaml` declara nodos
  (`ollama` local y otros por IP en la zona de IA o por WireGuard) y qué modelos sirve cada uno;
  el gateway comprueba su salud, reparte y hace failover. Un segundo mini-PC con Ollama se añade
  con dos líneas y una regla de firewall (documentado).
- **Cloud burst controlado**: upstreams de tipo `openai` (cualquier API compatible: OpenAI,
  OpenRouter, Groq…) marcados como `cloud: true`. Solo las llaves con `cloud: true` pueden usar
  esos modelos; hay presupuesto mensual en USD por llave y global con tabla de precios en la
  config; cada evento de auditoría lleva `cloud=true`; alerta en Grafana al superar el 80 % del
  presupuesto. Las credenciales del proveedor van en `compose/.env` (`GATEWAY_UPSTREAM_<NOMBRE>_KEY`).
- **Compatibilidad**: la ruta `api.<DOMAIN>/v1` y `http://gateway:4000/v1` dentro de `gd_agents`
  no cambian para los clientes; los eventos de auditoría mantienen el esquema `llm_request`
  (`service` pasa a `gateway`); los paneles aceptan ambos. Las llaves de LiteLLM no se migran
  (están hasheadas): `guardianctl key create` las vuelve a emitir. LiteLLM y su Postgres
  desaparecen del compose; el volumen antiguo se puede borrar tras migrar.
- **Imagen propia** construida en local desde bases fijadas por digest (builder `golang`,
  runtime `gcr.io/distroless/static`), sin publicar imágenes.

## Criterios de aceptación

- Una app con llave virtual llama a `https://api.<DOMAIN>/v1/chat/completions` (con y sin
  `stream`) y obtiene la misma respuesta que con LiteLLM; modelo no permitido → 403; llave
  inválida → 401; más de `rpm` peticiones → 429.
- Con dos nodos, apagar uno no interrumpe el servicio; `doctor` lo refleja.
- Un modelo `cloud` solo responde a llaves con `cloud: true`; el gasto se acumula y al 80 % del
  presupuesto llega una alerta ntfy; al 100 % → 402.
- Consumo de memoria del gateway < 50 MB frente a > 1 GB de LiteLLM + Postgres.
- Paneles LLM y alertas siguen funcionando; puertos publicados sin cambios; CI en verde.

## Restricciones

Las de siempre. El gateway no guarda prompts ni respuestas (solo metadatos). Solo stdlib.
